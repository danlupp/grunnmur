# 06 — Change extraction

Stage 5 of the pipeline. Two independent extractors feed one reconciliation step. The independence
is the point: each is a check on the other.

## 6.1 Footnote-0 annotations

Lovdata places a footnote 0 directly beneath each paragraph carrying that paragraph's change
history. These strings are highly formulaic and reach back decades — considerably further than
Lovtidend's 2001 horizon. They are the single highest-value extraction target in the project.

Representative forms:

```
Endret ved lover 17 juni 2005 nr. 62 (i kraft 1 jan 2006 iflg. res. 17 juni 2005 nr. 603),
    21 des 2005 nr. 121.
Tilføyd ved lov 19 juni 2009 nr. 39.
Opphevet ved lov 15 juni 2018 nr. 38 (i kraft 1 juli 2018).
Endret ved forskrift 7 des 2012 nr. 1173.
Endret ved lov 20 des 2019 nr. 100 (i kraft fra den tid Kongen bestemmer).
```

### Grammar first, model second

Use a **deterministic PEG grammar** as the primary extractor. These strings are generated by
Lovdata's own tooling, so a grammar will cover the overwhelming majority exactly, cheaply, and
reproducibly — and, critically, its failures are *loud* rather than plausible.

```ebnf
note        <- verb ws "ved" ws source_list "."
verb        <- "Endret" / "Tilføyd" / "Opphevet" / "Endres" / "Tilf" ...
source_list <- source (ws? "," ws? source)*
source      <- doctype ws nor_date ws "nr." ws number ("(" in_force ")")?
doctype     <- "lov" / "lover" / "forskrift" / "forskrifter" / "res" / "vedtak"
in_force    <- "i kraft" ws (nor_date / "straks" / kongen) (ws "iflg." ws res_ref)?
kongen      <- "fra den tid Kongen bestemmer"
nor_date    <- day ws nor_month ws year
nor_month   <- "jan"/"feb"/"mars"/"april"/"mai"/"juni"/"juli"/"aug"/"sep"/"okt"/"nov"/"des"
res_ref     <- "res." ws nor_date ws "nr." ws number
```

Each parsed `source` yields one `change_event`:

| Field | From |
| --- | --- |
| `changing_work` | `doctype` + `nor_date` + `number` → `LOV-2005-06-17-62` |
| `changed_work` / `changed_prov` | The document and provision the footnote hangs under |
| `operation` | `verb` → `amend` / `insert` / `repeal` |
| `in_force_on` | `in_force` date, `null` for *kongen bestemmer* |
| `in_force_source` | `res_ref` |
| `retroactive` | `in_force_on < kunngjort_on` |
| `evidence.confidence` | `1.00` on a clean parse |

**Unparsed residue** goes to a queue, never silently dropped. Triage it in two ways: extend the
grammar when a form recurs (the right fix, and the residue rate is the metric to watch), and use an
LLM extractor as a *fallback only*, emitting `evidence.method = 'llm-assist'` with
`confidence ≤ 0.7` — which routes it to human review before it can affect a published interval.

The ordering matters and is not a matter of taste: an LLM as the primary extractor would be
non-reproducible across runs, which forfeits the audit property that justifies the entire
bitemporal design.

## 6.2 Lovtidend change acts

Change acts state their operations in structured prose:

```
I lov 17. juni 2005 nr. 62 om arbeidsmiljø ... gjøres følgende endringer:

§ 5-3 andre ledd skal lyde:
    <new text>

§ 5-4 oppheves.

Loven trer i kraft 1. januar 2026.
```

Extraction is a two-level parse: an **operation grammar** over the instruction lines
(`§ X skal lyde` → amend, `§ X oppheves` → repeal, `Ny § X skal lyde` → insert, `§ X blir ny § Y` →
renumber), and a **provision-reference grammar** over the designators (`§ 5-3 andre ledd bokstav a`)
that produces a `logical_key` matching [03 §3.2](03-entity-model.md#32-identity--the-trap-worth-ten-pages).

The `logical_key` normaliser is shared code between this parser, the footnote parser, and stage 3.
Any divergence between the three shows up as spurious unmatched provisions, so it belongs in one
module with its own test suite — this is the piece most worth over-testing.

The trailing entry-into-force clause is parsed separately: it may set a date, delegate to the
Crown, or set different dates per provision (staged entry into force → one `change_event` per
provision, not one per act).

## 6.3 Reconciliation

Three streams, one truth table. For each detected text change:

| Diff says | Event says | Action |
| --- | --- | --- |
| changed | matching event, date ≤ diff date | ✅ Apply. Valid from the event date, tx from the snapshot |
| changed | matching event, date > diff date | ✅ Apply, flag `early_consolidation` — Lovdata applied a future-dated change; the provision is `not_yet_in_force` until the date arrives |
| changed | **no event** | ❗ Block. Review queue. Usually an unparsed footnote or a *rettelse* |
| changed | event exists, but the change is whitespace-only after canonicalisation | Ignore. Do not create a version |
| unchanged | event exists | Flag `pending_consolidation` — promulgated, not yet in the consolidated text. Track as `state = 'pending'` |
| absent | repeal event | ✅ Close the valid interval at the repeal date |
| absent | **no event** | ❗ Block. Possible bad fetch — see [05 stage 4](05-pipeline.md#stage-4) |

`pending_consolidation` is worth dwelling on: it means the law has changed but Lovdata's
consolidated text has not caught up. Surfacing that lag is a real feature — it is precisely the
window in which every other Norwegian legal database is quietly wrong.

## 6.4 Reference extraction

Separate pass over the parsed text, producing `edge` rows of kind `cites`.

1. **Explicit links** — Lovdata marks internal and cross-document references in the markup. High
   confidence, near-free.
2. **Textual patterns** — `§ 5-3`, `jf. § 4 andre ledd`, `kapittel 3`, and named-act references
   (`forvaltningsloven`, `straffeloven`). Maintain a curated short-title → `work_id` lexicon; the
   named-act vocabulary is small, closed, and slow-moving, so a lexicon beats inference.
3. **Resolution** — bare `§ 5` resolves within the citing document; a named reference resolves to
   that work's `logical_key`. Unresolvable references are stored with `dst_raw` populated and
   `dst_work = null`, never dropped.
4. ❗ **Style** — default `ref_style = 'dynamic'`, which is correct for the overwhelming majority of
   Norwegian legal drafting. Mark `static` only on an explicit textual cue ("slik den lød",
   "som gjaldt da"). See [03 §3.4](03-entity-model.md#referential) for why this distinction changes
   query results rather than merely annotating them.

## 6.5 Quality metrics

Track these per run and alert on regressions; they are the health of the whole system:

- **Footnote parse rate** — target > 99 %. The residue is your grammar backlog.
- **Unexplained change rate** — target 0. Anything above it is blocked work sitting in review.
- **Reference resolution rate** — track by kind; internal should approach 100 %, cross-act lower.
- **Review queue depth and age** — if this grows without bound the pipeline is not actually
  automated, it is just deferred.
- **Consolidation lag** — days between `in_force_on` and the snapshot that first shows the text.
  Interesting in its own right, and the best early warning that an upstream format change has
  broken extraction.
